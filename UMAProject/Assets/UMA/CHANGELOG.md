# Changelog

## 3.1f6 (package version 3.1.6)

Changes since **3.1f5 / 3.1.5** (`V3.1.5`). Unity 6.3 and newer are supported. The 3.1f5 entries below remain the record of that release.

### Installation, configuration, and validation

- **Hair Card Tests** now installs to `Assets/UMA/HairCardsTests`, beside the plugin instead of inside it, like Overlay Painter Tests. Installing Hair Card Tests again moves a copy from the old `Assets/UMA/HairCards/Editor/Tests` folder to the new one, keeping its GUIDs, before replacing it; if both folders exist, the install stops and asks you to delete the older copy. Reinstalling Hair Cards leaves the old copy in place.
- Fixed **Reinstall All Plugins** stopping at **Dismemberment Examples** with "Installed content does not match the archive: U3-GoreExample.unity" and rolling that package back. Unity's package import opens an imported scene and saves it again when it upgrades the scene's lighting settings, so the scene's bytes no longer matched the archive. The installer now accepts a scene that Unity rewrote during the import, as long as its `.meta` (GUID and import settings) still matches the archive; every other file keeps the exact byte check. The Gore example scene also ships already saved by Unity 6000.3, so it installs unchanged.
- Plugin installs and removals, and the render-pipeline (SRP) support install on the **Welcome to UMA** window, no longer stall while Unity is in the background. After each domain reload the installer resumed through `EditorApplication.delayCall`, which Unity only runs after the inspectors repaint, and an unfocused Editor does not repaint them, so **Reinstall All Plugins** paused after every package until you switched back. The SRP support install waited the same way after its import finished. Both now resume from the Editor update loop once compiling and importing finish. While install, download or removal work is running, UMA also keeps the Editor updating with Unity's internal `EditorApplication.SignalTick`; if a Unity version removes or changes that call, UMA falls back to Unity's normal background rate. A minimized or fully covered Editor window may still pause.
- **UMA > Build > Rebuild Active SRP Manifest** now warns (in the Console and in its closing dialog) about UMAMaterials whose material is missing or outside `Assets/UMA/SRP`. The manifest only lists files in that folder, so before this the problem only showed up as the "Exclude broken UMA materials?" prompt when building the package.
- Fixed the URP package build asking to exclude `UMAMaterial_UMA_SRP_DiffuseAlpha`: its material, `UMA_SRP_DiffuseAlpha_URP`, was in `Assets/UMA/ShaderPackages` and was never packaged. It now lives in `Assets/UMA/SRP/ShaderGraphs/Materials`, with the same GUID, so existing references still work.
- The HDRP support package is built from HDRP sources again. The HDRP shader graphs and materials, the eye diffusion profile, the `HDRPSetup` prefab and the HDRP sample volume profiles were missing from `Assets/UMA/SRP` and are restored from the last published `UMAHDRP.unitypackage`, and the 11 UMA lit Shader Graphs (`UMALitShader`, `UMA3_Lit(Metal)`, `UMA3_Lit(Specular)` and the others) target HDRP as well as URP again. Every HDRP pass of the UMA graphs compiles.
- The SRP package build (**UMA > Build**) now decides which package a file belongs to from what it contains instead of from its name: a Shader Graph by the pipelines it targets, a shader by the `RenderPipeline` tags of its SubShaders, an `.hlsl` include by the shaders and graphs that use it, and a material by its shader and by the UMAMaterial field that uses it (the URP or the HDRP material). Files that both pipelines use go into both packages. The HDRP package ships `ShaderGraphs/Graphs/Helpers/U3EnvironmentHDRP.prefab` as `Environment/U3Environment.prefab`, at the same path and GUID, so the sample scenes keep their environment; scene overrides of its light intensities, which are in URP units, are left out of the HDRP copies of the scenes, and so are their references to the URP-only `Settings/SampleSceneProfile.asset`. Binary assets are never read as text.
- The HDRP setup prefab (`HDRPSetup/UMAHDRPSetup`) only registers the UMA diffusion profile and HDRP settings while HDRP is the active render pipeline. In a project that has the HDRP package installed but renders with URP, a queued setup is dropped instead of changing HDRP's global settings.
- New slots, overlays and races are now added to the **Global Library** automatically when they are created, imported, duplicated or moved into the project, and removed from it when they are deleted; a moved or renamed asset keeps its entry with the new path or name. Once an import has finished, the library asset is saved once, on its own (no other asset is saved), and the save writes only that import's changes: every other library item is written exactly as the file already stores it, and items that only exist in memory, such as runtime-baked slots, are left out. Each change is reported in the Console and in a short Scene view notification. Assets with **No Auto Add** set are skipped, as are new assets outside the type's **Global Library Filters** folders (listed in the Console) and duplicates whose slot, overlay or race name is already in the library (a warning names both). Nothing is registered in Play mode, during player builds, in batch mode, while UMA plugins install or uninstall, or during Unity Test Framework runs. Turn it off with **Auto-add to Global Library** in **Project Settings > UMA**. See [the Global Library guide](Docs/UMAAssetIndexer.md#automatic-registration).
- **Scripts that need a `using UMA;`:** the 42 UMA source files that declared their types outside any namespace are now in the `UMA` namespace, among them `DNAEditor`, `DNAGroupEditor`, `DynamicExpression`, `DynamicExpressionPlayer`, `DynamicExpressionLegacyAdapter`, `IconCreator`, `SceneNote`, `UMATaskItem`, `UMATextureSaver`, `UMAAnimationParameterSetter`, `BaseUpdatedObject`, `DNACurve`, `RaceCompatibilityModifier`, `SlotBurnOptions`, `StatDisplayer` and the Dismemberment sample scripts. Scenes, prefabs and assets that use them load unchanged (Unity finds scripts by file GUID). Your own scripts that name one of these types need `using UMA;` or the full name `UMA.TypeName`.

### Recipe and character editing

- Added **Assets > UMA > Add a slot to selected recipes** for selected wardrobe and text recipes. A dialog takes the slot, its matching criteria (tags, the races it is added for, and the swap-slot setting) and, optionally, overlays and shared colors, and adds them to every selected recipe as one undo step. Recipes that already have the slot are left alone and listed. Whatever a recipe already holds is kept as it is, including slots and overlays the Global Library cannot find. See [batch utilities](Docs/AssetMenuBatchUtilities.md#add-a-slot-to-selected-recipes).
- The DynamicCharacterAvatar inspector has a new **Editing tools** section, just below **Character & race** and in Standard as well as Advanced view, with the editors that used to be under **Utilities** at the bottom of Advanced view: **Open Vertex Editor (Sculpt, Paint, Mesh Modifiers)** (was **Create New Mesh Modifier**), **Open Face Editor (Mesh Hide Assets)** (was **Create New Mesh Hide Asset**), **Touchup Weights**, **Create Slot From Scene Mesh**, and the drop box for editing an existing Mesh Modifier, Mesh Hide Asset or Mesh Hide Collection. Each button says what its editor does, and the section's Help describes them in full. The section folds away, and remembers whether it is open. With **Editor Time Generation** off the section stays visible, says why its buttons are disabled, and has a button to turn it on.
- Reorganized the DynamicCharacterAvatar inspector's **Advanced View** into foldable panels grouped by job, like Standard View's sections: **Character & race** (with User Information and the race change options), **Editing tools**, **Wardrobe** (with Additional Utility Recipes and the current wardrobe), **Colors**, **Body shape & DNA** (with blendshape loading), **Animation**, **Generation**, **Build behaviour**, **Performance & sharing**, **Rendering**, **Bounds**, **Addressables**, **Events**, **Diagnostics** (Loop Build, cache diagnostics, manual Mesh Modifiers, UMA Data, the placeholder model) and **Legacy Load/Save**. The long **Advanced Options** list, the **Customization** box and the **Utilities** foldout are gone; their settings are in those panels. The global **Show Help** toggle, which put a help box above every field, is replaced by each panel's **Help**, which describes all of its settings; the Events panel no longer shows a help box above every event. The first five panels start open and the rest folded, and each remembers whether it is open as an editor preference, never on the avatar. Current Wardrobe and the manual Mesh Modifiers stay in place when the character is not built and say what is needed. Standard View is unchanged. Inspector sections can now fold (`UMAInspectorView.CollapsibleSection`).
- Added **Assets > UMA > Manage Color Parameters** for selected Shared Color Tables. It adds a shader parameter to every color, or updates it where a color already has one. The value is either fixed, or each color's own value of a parameter multiplied by a number (for example `_SpecularMultiplier` x 1.2). Colors without the source parameter can take the material's value (what they showed until now), the fixed value, or be skipped. Parameters are picked from a material, which is remembered per project in `UserSettings`. A preview lists every color's old and new value; Apply supports Undo, removes duplicate entries of the parameter, and saves only the changed tables.
- The UMAMaterial inspector's **Material Preview** now updates both passes of a two-pass UMAMaterial, such as the UMA 3 hair. A property changed in the preview (which shows the first-pass material) is also changed on the **Second Pass** material when that material has it, along with a shader keyword of the same name (for example `_EMISSION`). Undoing the change undoes it on both. The settings that make the passes different are never copied: surface type, blending, depth, culling, stencil, alpha clipping and shadow casting. The preview avatar's generated materials of both passes follow their own pass's material, keeping the textures UMA built for them, and **Save material changes to disk** saves both materials. Before, only first-pass materials on the avatar were updated, because the second pass was skipped when its shader or name differed. Properties that already differ between the two hair materials, such as **Alpha Modulation**, take the edited value on both when changed in the preview.
- Fixed edits in a DNA asset's effect panels (curves, mapping values, names, the enabled toggle, **Enable all**, **Disable all**, **Remove**, **Remove Selected**) never being saved. The DNA inspector changed the effects in memory without marking the asset as changed, so **Save Project** skipped it, closing Unity could lose the edit, and **Duplicate** copied the old values from disk. The asset is now marked changed and saves with the project. Folding an effect open or closed does not mark it.
- The Vertex Editor's **Save as Mesh Modifier** saves one Mesh Modifier per wardrobe recipe whose slots you changed, and asks whether to add each to its recipe. For example, edits to a shirt and to pants become `<name>_Shirt.asset` and `<name>_Pants.asset`, added to the shirt and the pants recipes, so each recipe carries only the changes to its own slots. Changes to slots no worn wardrobe recipe has (the body) go in the file you choose and are not added to a recipe; with only one recipe (or none) involved, everything goes in the file you choose, as before. The question lists every file, says which ones replace an existing file, and offers **Save Only** to change no recipe. When the editor was opened on an existing Mesh Modifier, it is saved whole to the file you choose and no recipe changes, so a modifier one recipe carries for other slots (a hair's scalp shading on the body) stays together. While the editor stays open, the character does not also apply a modifier it just added to a recipe (the editor already shows those changes); after you leave, the character wears it through the recipe.
- Fixed **Vertex Paint** hiding the vertex colors a character gets from its worn recipes' Mesh Modifiers, such as the scalp shading of the UMA 3 hair. Starting Vertex Paint replaced them with the slot's own colors, so the shading vanished from the preview and could not be found to edit. Vertex Paint now starts from the colors the character shows: the slot's own colors, then the worn recipes' Mesh Modifiers, then the modifier being edited, so editing a modifier keeps every color it had, not only the vertices painted. Paint is still saved as only what you painted, on top of them, and **Save Vertex Colors to Slot** writes the slot without the recipes' colors, so they are not applied twice. When a worn recipe's Mesh Modifier colors any of the editable slots, the Vertex Paint panel names it (with the slots it colors) and offers **Edit**, whichever slot the brush is on: the editor asks about unsaved work, then opens again with that modifier loaded, so its colors can be painted and saving updates the asset in place.
- Fixed the Vertex Editor showing the character magenta when the character was built again while the editor was open, for example by a build that leaving the editor had queued, or one an inspector started. The build destroyed the materials the editor's preview had taken; the preview now takes the character's new materials and keeps the character's own renderer hidden. Vertex Paint's **Edit** button also waits for the build that leaving queues before it opens the editor again, and works while Unity is in the background (it does not rely on delayCall). `DynamicCharacterAvatar` has `EditorGenerationQueued` and `RunQueuedEditorGeneration()` for editor tools that need the queued edit-time build out of the way.
- Fixed the Vertex Editor showing a Mesh Modifier twice when opened on one that a worn recipe already uses. From the first rebuild in the editor (**Rebuild Now**, Undo, **Rebuild on changes**), the recipe applied the modifier and the editor applied it again, so the scalp shadows of the UMA 3 hair looked 86% dark instead of 62%, and a sculpt moved twice as far. The editor now applies that modifier itself and the recipe skips it until you leave. The saved assets were never affected; only the preview was.
- Fixed UMA failing to compile on Unity 6.6: two calls in the resource reuse cache passed `null` where Unity 6.6 can also convert it to a `Vector2`, so the call was ambiguous.
- Fixed recipe saves that could lose or change stored data:
  - **A missing slot is no longer erased by an unrelated edit.** When a recipe names a slot the project does not have, loading leaves it out (it used to do so silently). The load now records it (`UMAData.UMARecipe.missingAssets`), and both inspector views treat the recipe as not fully loaded: Standard View refuses edits, and Advanced View disables editing until you choose **Enable Editing**. Nothing writes the partial recipe back, including **Save Recipe** (Automatic Updates off), leaving the inspector, plugin actions, the slot and overlay editors (which save the recipe themselves), and drag and drop onto the locked inspector; before, **Save Recipe** saved it even after a failed load. Advanced View also stays locked below the compatible races: drawing a race's name re-enabled every control under it.
  - **A missing overlay no longer stops the load.** The Global Library throws for an overlay it does not have, so loading stopped there and every slot and overlay after it was left out (and lost if the recipe was then saved after **Enable Editing**). A missing overlay is now recorded and skipped like a missing slot, and the rest of the recipe loads; at runtime too, a character now builds without the missing overlay instead of failing. Version 1 and 2 recipes with a missing slot no longer fail with a `NullReferenceException`. When the missing slot is one whose overlays other slots share, those slots now load the overlays stored with it (they loaded with none, and saving removed the overlays from the recipe).
  - **Enable Editing applies to one failed load.** It used to stay on when the recipe was reloaded, even if a different asset was now missing, and a reload that succeeded left Advanced View disabled.
  - **Integer shader properties keep their names.** Each save added `***` to the name (`_Mode` became `_Mode***`, then `_Mode******`), so the property no longer matched the shader. Names written that way are repaired when the recipe loads.
  - **Opening Wardrobe Settings no longer clears Replaces.** A stored slot that is not among the base slots found for the compatible races is shown as its own choice and kept; the value changes only when you pick another.
  - **Slots whose overlays differ are no longer merged on save.** Saving (and building a character) shares one overlay list between slots whose overlays match. The match now includes rotation, scale, translation, transform flag, UV set, tiling, blend modes, tags and shader properties, so two slots with, for example, differently rotated copies of an overlay keep their own values.
  - **Placeholder slot overlays keep their position and blending.** Reloading restored only rect, tags and color; it now restores everything the recipe stores, as for ordinary overlays.
  - **An overlay keeps its own UV set.** Reloading gave each overlay its slot's UV set (a different setting); it now reads the overlay's own value. Building a character does not use the overlay value, so characters look the same.
  - **Local colors that differ only in shader properties stay apart.** Saving stored them as one color entry, so on reload every overlay had the first one's shader tint.
  - **Recipes with array shader properties load.** Texture, array, matrix and buffer properties reloaded named `0`, and copying an array property that had no values (as every loaded one is) threw, so a recipe with one in an unshared color failed to load.
  - **HDR shader colors keep their values.** Colors were stored as 8-bit hex, so an emission value of 4 came back as 1. A color within 0–1 is stored as before; one outside it is stored as four numbers (older UMA versions read those as white).
  - **A placeholder slot cannot be given an empty name.** A placeholder with no name is not saved, so clearing the name removed the slot and its overlays on save. The empty name is refused and the current one kept.
  - **The Unity 6.4+ Wardrobe Recipe Graph writes each edit to the wardrobe asset with Unity Undo.** Auto Save writes that asset to disk after each edit. With Auto Save off, other editors can see the edits immediately, and **Save** or **File > Save Project** writes them to disk. Undo and Redo work in both modes. Notes, node positions and detached overlays travel with the asset and with **Save As** copies. Existing local notes and positions migrate on a graph edit or explicit Save. Pan, zoom and panel width remain personal preferences. The graph reloads outside edits and blocks saving recipes with missing data. **Save As** can create a separate copy of the parts that loaded. Dropping slots, overlays and recipes on the graph makes the same checks as the recipe inspector (the Global Library asset, a recipe that did not load completely), and so do the graph's slot and overlay pickers and its **Stack Overlay** field. Dropping slots with several overlays puts the overlays on the first slot the drop added; they went on the selected slot, an existing one (when every dropped slot was already in the recipe, they become separate overlay nodes). The selected node's slot and overlay controls are kept between redraws, so an asset picker they open delivers its choice, and are rebuilt when the overlays are reordered: Remove on a row after a reorder removed another overlay. Connecting an overlay that is already on one slot to a slot with overlays of its own adds a copy of that overlay there; it replaced the target slot's overlays with the first slot's whole stack. A slot with no overlays still shares the whole stack. Dragging an overlay's connection to another slot moves that one overlay; the target slot was given the source slot's whole list (the moved overlay and the ones left behind) in place of its own. Typing in a note is one Undo step per note (it was one per character), and with Auto Save on it is written to disk when you leave the note (it was written on every keystroke). Slots whose overlays all match are still stored once in the recipe file, but the graph keeps each slot's own overlays while you edit: as soon as two stacks matched, the second slot's overlay nodes vanished and editing one slot changed both. A slot that shares another slot's overlays says so in its panel and has **Give This Slot Its Own Overlays**.
  - **Stored values come back as saved.** A slot scale of 53% was saved as 52% (the scale was truncated, not rounded). A color's own display swatch (**Show Display Color**) came back as the first channel's color; the swatch and the setting are now stored, and two local colors that differ only there are no longer saved as one. Saving no longer links two overlay stacks that differ only in their swatch (they shared one list, and both took one swatch). An overlay keeps the shared color it is linked to when the recipe is saved; it was linked to the first shared color that looked the same, and a local color could be linked to a shared one. Slots whose overlays use two different shared colors with the same name are no longer linked into one overlay stack by a save. Small shader values keep their precision: a float, vector or overlay transform value was written with four decimals, so 0.00004 came back as 0 (values four decimals hold are written as before). DNA of a type the project does not have (such as an older UMA DNA class) is kept and written back on save, also when the recipe is merged into another by dropping it (the merged recipe's values win, as they do for DNA that loaded); the load left it out, and an unrelated edit removed it for good. A version 2 recipe keeps a shader-parameter-only shared color without channels, as version 3 does.
  - **Colors keep their shader settings on reload.** A color made with **Add Shared Color Parms** (shader parameters, no channels) came back with its name only, losing its parameters. A color whose shader settings held only **Always Update** came back without it, and when saving merged local colors it counted as the same as a color with no shader settings. A color with no channels kept its swatch color (it was stored as white). **Add Shared Color Parms** gives the new color shader settings to fill in, and **Add Shader Property Block** is offered for every color (only colors with channels had it). An empty overlay's property picker starts at **(not linked)**: it showed the first property as chosen without linking it, and with one property, choosing it changed nothing. Choosing **(not linked)** on a linked overlay unlinks it (keeping its values). A shader-parameter-only shared color linked to an overlay keeps having no channels when the recipe loads; loading expanded it to the overlay material's channels, and it dropped out of the property picker.
  - **A new recipe with no slots can be saved.** Adding a shared color, or **Save As**, failed on a recipe that had never had a slot. **Save As** now fills in the copy before creating its file, so a failure no longer leaves a half-made asset.
- Fixed Advanced View wardrobe recipe editing:
  - **Wardrobe region** saves the race's region key. A region found on only some compatible races was saved with its label (`Tail  (Dragon Only)`), which characters do not recognise, so the item did not appear. When the region list cannot be built (no compatible race, or one is missing), the stored region is shown and kept instead of being set to None.
  - The compatible race, hidden slot and Mesh Modifications pickers add what you pick when the picker closes. They added every asset highlighted while browsing, and cancelling kept them.
  - A race listed twice no longer breaks Race Settings (Standard View no longer lets you add one twice), and gets one thumbnail, the last one with a sprite when there are several (the one characters use): its thumbnails used to double, and be saved, on every redraw of the inspector. With no compatible races, Race Settings keeps the stored thumbnails; opening it cleared them. A race with no thumbnail of its own shows the first sprite in the list, which can be on an entry for a race that is no longer compatible; opening Race Settings removed that entry and the thumbnail with it. It is kept, listed as the default for races without their own, while a race uses it. A single compatible race with such a default can choose its own thumbnail row (the list showed only with two races or more). The **Wardrobe region** and **Hides** menus follow the compatible races however they changed; after **Copy Selected Values** or a change in Standard View they could still offer the previous races' choices. **Override DNA** lists only the races that were found, and **Add DNA** is disabled for a race with no DNA names; both used to throw.
  - With **Automatic Updates** off, adding or removing slots, overlays, mesh hides and modifiers, and leaving the inspector, keep the edits as unsaved changes until **Save Recipe** (or **File > Save Project**); before, several of them wrote the file at once. **Copy Selected Values** follows the same rule. **Clear Recipe** and **Remove Nulls** can be undone. Undoing an inspector edit with Automatic Updates off reloads the recipe; it was reported as a change made outside the inspector, whose **Use inspector edits** put the undone edit back. With Automatic Updates on, the restored recipe is saved. Only a recipe state the inspector itself had is reloaded this way, so an Undo while an outside change is waiting to be resolved keeps the pending edits. Standard View follows **Automatic Updates** too (it is shown there, with **Save Recipe**): it always saved, which also wrote pending Advanced View edits. Its unsaved edits count as pending, so a save from elsewhere is offered as a conflict instead of replacing them, and its **Save Recipe** also clears pending Advanced View edits it saved. A metadata-only Standard View edit (display name, region, thumbnails) no longer re-packs the recipe when the inspector closes, which could rewrite older recipe data during a rename. Edits written by **File > Save Project** no longer count as pending, and closing the inspector no longer marks such a recipe as unsaved again. Edits made with a slot's own controls (**Add Overlay**, removing an overlay, adding a shared slot) count as pending too; a later outside save replaced them without a conflict. A slot added from a slot's **Add Slot** gets its row at once. That control and **Add Overlay**, **Refresh slot from Asset** and removing a blendshape slot can be undone, as can the recipe's own **Add Slot**, **Add Base slot** and **Add Placeholder Slot**. **Add Placeholder Slot** gives each new placeholder its own name; a second press silently gave back the first placeholder. When the recipe changed elsewhere first, they are kept as pending edits instead of being written over that change. After a change with Automatic Updates off, the slot rows are rebuilt once: after **Clear Recipe** the cleared slots stayed on screen, and an added slot had no row. Removing one slot or one overlay can be undone. Dropping slots, overlays or recipes on the Advanced View's drop area, picking a slot there, and the generic recipe inspector's **Add Slot** and **Add Placeholder Slot** can be undone (the generic **Add Placeholder Slot** also gives each new placeholder its own name). The wardrobe inspector's **Save As** refuses an existing asset, the recipe itself included: choosing the recipe replaced it with a new asset (a new GUID, so every reference to it broke).
  - The **X** on a slot removes that slot after **Remove Nulls** or **Clear Recipe** with Automatic Updates off. It removed whichever slot had moved into its old position.
  - Dropping a Mesh Hide Asset Collection adds the collection itself, so later changes to it reach the recipe (it used to copy the collection's current members). **Add Mesh Hide Collection** picks one, and dropping a folder adds the mesh hides, collections and modifiers in it (folders added nothing before). Dropping slots with one overlay no longer adds them again on the next drop, and dropping a recipe that did not load completely asks before merging the parts that loaded. The indexed asset fields (slots, overlays) and the **Drag Slots, Overlays or Recipes here** area (dropped assets and folders alike) accept a slot or overlay only when the Global Library finds that same asset under its name, as their search list does; another asset with the same name looked right until the recipe was reopened. The others are listed in the Console, with any overlays dropped together with a refused slot (those went on whichever slot came first in the recipe). A drop in which everything was refused changes and saves nothing. Merging a recipe by dropping it keeps each slot's UV set and smoosh tags and each overlay's UV set and tiling; the copies left them out. Merging into a slot that already has the overlay takes the incoming overlay's transform, UV set, tiling, tags and blend modes along with its colors (only the colors came across), and an overlay without a material no longer makes the merge throw. Two of the dropped recipe's shared colors with the same name stay two colors; the merge gave every overlay of both the first one's values. A shared color the recipe already has under that name is still the one used, as at runtime. A recipe with two shared colors of one name no longer has the later ones renamed (`Skin.`) on each merge, which also stopped a character's `Skin` color from reaching them. An overlay merged into an existing placeholder slot keeps its shared color.
  - The overlay positioner's **Update Recipe** writes into the recipe at once (with Undo), so it is kept even when the recipe is no longer selected. When the recipe was saved from elsewhere (or reloaded) since the positioner opened, only the overlay's position goes into the recipe as it is now; writing the positioner's copy put back the older recipe (a slot saved from another inspector disappeared). If the overlay is no longer in the same place, nothing is written and a message says so. **Update Recipe** writes only what the positioner changed since it opened or last wrote (the rect, or the rotation, scale and translation); it also wrote the unchanged transform back over a newer rotation. When the recipe was changed elsewhere, the overlay is found there by its slot, its name and the values the positioner expects it to hold, so a layer reordered while the positioner was open is not mistaken for another; when two layers of one overlay both still hold those values, the one that matches the positioner's overlay in everything else (its color, UV set and shader settings) is written, not whichever layer is now in the old place; when it cannot be told, nothing is written and a message says so. **Cancel** puts the overlay asset's rect back only when this window changed it and nothing has changed it since. It does the same for the recipe: it puts back only what the positioner changed, and only while nothing else has changed it since; an untouched positioner's Cancel wrote its opening values back over a newer edit.
  - Opening an overlay in Advanced View no longer resets its colors when its material is missing (and a save then stored that).
  - Opening an overlay in Advanced View no longer clears its **UV Set** when its material is not a **Use Existing Textures** material; it is kept (and applies again with such a material), with a **Clear UV Set** button.
  - Standard View's help no longer says **Incompatible recipes** blocks recipes: UMA stores the list, and your application enforces it.
- Fixed recipe inspector edits that changed a recipe without saving it, so the edit was lost or never reached version control:
  - Wardrobe recipe **Mesh Modifications**: the **X** on a Mesh Modifier changed the recipe in memory only, and the **X** on a Mesh Hide Asset Collection did nothing. Removing a Mesh Modifier, Mesh Hide Asset or Mesh Hide Asset Collection now saves the recipe straight away, like other edits in the inspector, and can be undone. Empty entries in each list are cleaned up from their own list (empty Mesh Hide Asset entries were only removed when an empty collection entry was also there).
  - Dragging several Mesh Hide Assets or Mesh Modifiers onto a recipe added nothing after the first one that was already in the recipe. Adding one by drag or picker no longer fails with an error when the recipe's list has an empty entry.
  - A clipping-plane slot's **Clipping Parameters** discarded other slot edits made at the same moment, such as **Disable in recipe** or a placeholder rename.
  - A slot's **Matching Criteria** tags loaded with **Load** were not saved; tag edits are now saved whenever the list differs from the slot's tags.
  - **Add Shader Property Block** and **Remove Shader Property Block** on a shared color.
  - **Add** under a Wardrobe Collection's **Cover Images**.
  - Changing **RaceData** next to **Add DNA** on a new standard recipe.
- The recipe inspector's **Add to Global Index** buttons (on a slot, an overlay, the recipe's race, and a wardrobe recipe's compatible races) now save the Global Library alone, writing only the added item. Before, the slot, overlay and race buttons ran a full project save, which also wrote every other unsaved asset, and the compatible-race button did not save the library at all.
- `UMAAssetIndexer.ForceSave()` now saves the Global Library asset alone. ### Generation, animation, and physics

- **Behavior change: active objects tagged UMAIgnore are now always kept when the skeleton is rebuilt.** An object tagged **UMAIgnore** under a character's bones (a weapon in the hand, for example) used to be kept through a rebuild that replaces the skeleton (a race change, a new rig) only when the generator's **Save And Restore Ignored Items** was on; with it off, it was destroyed with the skeleton without a word. Active tagged objects are now found through Unity's tag list instead of a walk over the bones (about 0.3 µs against about 116 µs for a 230-bone character, and only when the skeleton is rebuilt), so they are kept with the option off too. Unity's tag list only holds active objects: an **inactive** tagged object is still only kept with **Save And Restore Ignored Items** on, which walks the bones and also keeps UMAKeepChain chains. To hide a mounted item without that option, keep its tagged object active and disable its child objects or its renderer instead. The shipped generator quality profiles (`QualityProfiles/HighPC` and `LowPC`) no longer override **Save And Restore Ignored Items**: they turned it off whenever a **Generator Quality Controller** applied them, although the default generator (`UMA_GLIB`) has it on.
- Added **Force GPU Texture Compression (Experimental)** to the generator (off by default, and turned off by **Welcome > Configure UMA**; also in Generator Quality Profiles and **UMA Generator Override**). Every generated Atlas and No Atlas texture is compressed on the GPU after it is composited, to BC3 where the device supports it and to ETC2 RGBA8 otherwise, and its RenderTexture is released: a quarter of the memory. In a Windows player, eight 2048 atlas channels with mips went from 170.7 MiB to 43.0 MiB. Where the device can copy the encoded blocks into a compressed texture on the GPU, nothing is read back; elsewhere, and always on OpenGL ES, the blocks are read back, a quarter of the data of a normal conversion. Devices without compute shaders, such as WebGL, ignore the switch. It takes the place of **Convert Render Texture** and runtime **Compression** for the textures it compresses, honours **Keep Converted Textures Readable**, and compressed and uncompressed atlases are never shared by atlas reuse. Save as prefab, Save Textures and the glTF exporter build the character without compression while they run. The ETC2 encoder is checked against Unity's ETC2 decoder but has not been run on Android or iOS hardware. See [UMA Generator Setup](Docs/UMAGeneratorSetup.md#force-gpu-texture-compression-experimental).
- Fixed "Instantiating a non-readable texture is not allowed" when a renderer needed its own copy of a generated atlas that has no CPU copy (a converted atlas with **Keep Converted Textures Readable** off): `UMAResourceLeaseOwner.MakeTextureUnique`, cloned generated renderers, script reloads, and the race T-pose editor's preview. Unity refuses to instantiate such a texture, and the copy did not hold the atlas. These atlases are now copied on the GPU (`UMAResourceLeaseOwner.CopyTexture`).
- Fixed hundreds of "Destroying object "Released UMA RT | ... | Temporary" is not allowed at this time" errors when leaving Play mode with **Convert Render Texture** and **Use Async Conversion** on. Leaving Play mode hands every atlas still waiting for its GPU readback back to Unity's temporary RenderTexture pool, but the character kept pointing at it, and its teardown then tried to destroy a texture Unity owned, once per channel per atlas. A cancelled or failed readback now clears the atlas entry it hands back, and UMA never destroys a temporary RenderTexture: one it still holds goes back to the pool, and one already returned is left to Unity.
- Converted textures no longer keep a CPU copy. With **Convert Render Texture** on, every converted Texture2D kept its pixels in system memory as well as on the GPU for its whole life, although only the GPU texture is used: in a Windows player, 21.4 MiB extra for each 2048 atlas channel (5.4 MiB when compressed), about 85 MiB for a character with a four-channel 2048 atlas. The new generator setting **Keep Converted Textures Readable** (off by default; also in Generator Quality Profiles and **UMA Generator Override**) keeps the copy for scripts that call `GetPixels` or `EncodeToPNG` on generated atlases. UMA's save, export and prefab tools work either way; **Save Character Prefab** (`PowerToolsRuntime`) now reads a GPU-only atlas back from the GPU, and frees the copies it makes. See [UMA Generator Setup](Docs/UMAGeneratorSetup.md).
- Fixed wrong colours in synchronously converted atlases. When the synchronous path read the atlas back on the CPU (with runtime **Compression** on, or when the GPU copy failed), it wrote the RenderTexture's RGBA bytes into an ARGB32 Texture2D, so every channel moved one place (red into alpha, green into red, and so on) before compression. The readback now converts to the Texture2D's own layout. Also, with compression off, a synchronously converted atlas was filled by a GPU-only copy and so held blank CPU pixels; a readable atlas is now always read back, so its CPU pixels match what is drawn.
- Fixed edit-time characters that stopped rebuilding. A DynamicCharacterAvatar queues its edit-time build with `EditorApplication.delayCall` and remembers that one is queued; a domain reload (any script change, or the Vertex and Face Editors closing themselves when scripts compile) dropped the queued callback but kept the flag, and from then on every edit-time build request of that avatar was ignored. Slots hidden in the Vertex Editor or Face Editor stayed hidden after leaving it, the character was not rebuilt after a script reload (so the next editor opened on it without its wardrobe), and the toolbar's **Rebuild** did nothing. The flag is no longer kept through a domain reload, and every build request now makes sure exactly one build is queued.
- Fixed characters built with the bone baking mesh combiners rendering much more slowly than other combiners when **Mark Dynamic** was on. Bone baking kept the mesh that renderer creation had marked dynamic, which is slow to render with GPU skinning; it now always fills a mesh of its own. **Mark Dynamic** is off in the sample character prefabs and in the Car, Timeline, and Photobooth sample scenes, and its help text states what it does.
- Sped up the Burst normal and tangent recalculation used by **Recalculate Normals** on a UMA Renderer Asset, `RecalculationSlot`, and slot baking with a smoothing angle: about five times faster on a 40,000-vertex character in the Editor. Each vertex position is now smoothed once instead of once per triangle corner. The result is also the same on every run: tangents no longer lose additions between threads, and a vertex whose own triangles fold past the smoothing angle always uses its first triangle as the reference. A small number of normals and tangents on such folds can therefore differ from earlier builds.
- **Recalculate Normals** no longer runs when it would write the same values again. The step now keeps a fingerprint of the mesh data and blendshape weights it used, and skips a build that changed neither, such as a texture-only rebuild or a rig update that moves no participating blendshape. On a 40,000-vertex character in the Editor a texture-only rebuild went from 29 ms to 16 ms and a rig-only rebuild from 13 ms to 6 ms. It also reads and writes the mesh without managed arrays, which removes about 2.8 MB of garbage per build, and no longer rewrites the UVs. `RecalculationSlot` uses the same code. A mesh without UVs gets normals only, and a mesh that has UVs but no tangent stream gets one.
- **Reuse Identical Meshes** now also helps renderers that use **Recalculate Normals**. Their meshes are still never shared with other avatars, but with the jobified combiner an avatar keeps its own mesh when a rebuild would produce the same one, and only the normals are recalculated if blendshape weights changed. Anything that changes the combined mesh, including a direct edit of the generated mesh, combines it again. The mesh reuse key now includes a slot's `expandAlongNormal`, which the combiners read but the key had left out. See [Atlas and mesh reuse](Docs/AtlasAndMeshReuse.md).
- Sped up filling an empty skeleton in the jobified and incremental mesh paths. The second time the same set of bones is requested, a hidden copy of that hierarchy is kept, and later skeletons are made by instantiating it: 15.8 ms to 5.4 ms for 228 bones in the Editor. This applies to a character's first build and to every recipe change with **Always Rebuild Skeleton**. Bone names, components, parents, sibling order and local transforms are the same as before; unusual input falls back to creating bones one at a time. At most eight hierarchies are kept, and they are released on script reload and when entering or leaving Play mode.
- A rig update keeps its humanoid Avatar when building it again would give the same one, which is the case whenever DNA has not changed (a colour or wardrobe change, for example). The Avatar is kept only when everything it is built from is identical: the same bone objects and parents, every bone's local position, rotation and scale bit for bit, and the same human description from the T-pose asset. The stored human pose is then applied through the kept Avatar with the same call a rebuild uses, so the bones end up exactly where a rebuild leaves them. On a 229-bone character the rig stage went from 5.2 ms to 2.7 ms with the Editor in the background (1.9 ms to 0.9 ms focused). **Keep Avatar** is unchanged and still skips the step without comparing. Generic races and bone-baking skeletons always rebuild as before.
- Reduced blendshape and mesh-hide work in the jobified combiner. Blendshape frames share one set of buffers and clear only what the previous frame wrote, and a triangle mask is converted and counted in one pass.
- Cloth now behaves the same with every mesh combiner. A renderer gets a Unity `Cloth` component when its slots carry cloth coefficients (copied from a `Cloth` component on the source mesh when the slot was built). The UMA Renderer Asset's **Cloth Properties** only tune that cloth; without them it runs on Unity's default Cloth settings. Before, the default combiner's standard path removed such cloth when the renderer had no Cloth Properties and added cloth to the whole renderer when it had Cloth Properties but no coefficients, and its MeshAPI path threw a `NullReferenceException` after adding the cloth. To remove cloth from a slot, clear all of its **Cloth Skinning Serialized** entries.
- Added **Disable Hair Control at LOD** to `UMASimpleLOD` (Runtime feature reduction; -1, the default, leaves it unmanaged). At and beyond that LOD zone the **UMA > Hair Control** components on the character and below it are disabled, which stops the sway, sends the hair volume shading back to the renderer bounds, and gives the hair renderers back to the SRP Batcher; coming closer enables them again with the hair at rest, and a rebuild applies the current zone again. See [UMASimpleLOD](Docs/UMASimpleLOD.md).
- The random-character sample's timing overlay is now the **UMA Timing Overlay** object in that scene (component **UMA > Timing Overlay**), so it does not depend on where the UMA folder is installed, and it draws its text with Unity's built-in font, so it needs no font file in the project. It is compiled into its own `UMA.Timing` assembly (referencing `UMA_Core`), so a Package Manager install of UMA Core adds no script to the project's `Assembly-CSharp`.
- Fixed the **Bone Transform** DNA effect (`DNAEffect_BoneTransform`) moving a bone away from its values instead of toward them, and treating the rotation differently from the position and scale. It now offsets the bone the way a Bone Pose does for a single bone: **Position Offset** is added, **Rotation Offset** is applied on top of the current rotation, and **Scale Multiplier** multiplies the current scale, each by the mapped DNA value. It stacks with Bone Pose and the other bone effects, and an effect left at position `0,0,0`, rotation `0,0,0` and scale `1,1,1` changes nothing. The values are no longer a target transform; a DNA asset that used this effect needs its values entered again as offsets (no UMA DNA asset used it).
- Fixed the **Overlay UV Transform** DNA effect (`DNAEffect_OverlayUVTransform`), which did nothing on most overlays and shrank the overlay to nothing where it did work. It now marks the overlay as transformed so the texture build reads it, goes from untransformed at a mapped value of 0 to the full **Offset**, **Scale** and **Rotation** at 1, is applied again when its DNA slider moves on a loaded character, and clears the transform when the value goes back. It replaces any transform the recipe stores for that overlay, and it cannot transform a slot's base overlay.
- The **Shared Color** and **Shared Color Property** DNA effects now also write their value when the DNA is at its default value, as **Shared Color Channel** already did. Before, taking a slider back to its default (or pressing its reset button) left the color of the last other value on the character. A DNA that uses them now sets its color at the default value too.
- DNA blendshape weights are now set at the end of every build. A build that left the rig alone (a color or mesh modifier change, for example) did not set them, so a DNA that combined a **Blend Shape** effect with a color or mesh modifier effect, and no bone effect, did not move its blendshape when the slider changed.
- The **Runtime Material Property** DNA effect (`DNAEffect_RuntimeMaterialProperty`) now works on ordinary character DNA as well as in a Dynamic Expression Player: the property is written at the end of every build and whenever the DNA value changes, with no build of its own. It reports the new `DNABuildType.MaterialProperty`. A texture slot left empty no longer throws; the property is left as it is.
- Saved characters no longer store a DNA group reference with each DNA value. It was written as a session-specific object identifier (Unity's EntityId, under the name `instanceID`), which made the same character save as different text in every session and could not be resolved in a later one. Saved text now holds the DNA names, values and enabled flags only, and an identifier found in older text is ignored on load; the group is found again by DNA name.
- The **ElfEars** DNA now runs from 0 (no elf ears) to 1 (full elf ears) with a default of 0. Its default used to be 0.5, where the ears were skipped, so a character had no elf ears at exactly 0.5 and about half of them at any value just beside it. Values other than 0.5 look as they did. A character saved with ElfEars at the old default of 0.5 now shows half elf ears; set it to 0 for none. The UMA 3 presets, the Getting Started avatar prefabs and the sample scenes that held 0.5 have been set to 0, so they look as before.
- The DNA inspector's **Performance and validation** section warns when an effect that is skipped at the DNA's default value (a mesh modifier, for example) has a mapping that gives a value there, since the character then jumps as soon as the slider leaves the default.
- Fixed a wardrobe item cleared for a race change coming back on a later change to the same race. When the race changes in Play mode, DynamicCharacterAvatar caches the state of the race it leaves (**Cache Current State**, on by default) and restores it on the way back. That state was read from the wardrobe at the moment `ChangeRace` was called, so a script that first dressed the avatar for the next race (for example `ClearWearableItems("Tail")` and new ears, then `ChangeRace("Human")`, with or without `BuildCharacter()` in between) had that outfit cached as the old race's. With **Keep Wardrobe** on, the second change to Human then filled the emptied Tail slot from the outfit cached under "Human", which was really the catfolk's, tail included; without Keep Wardrobe, returning to a race brought back the previous race's outfit instead of its own. The cached state now holds the wardrobe the generator last built as that race; a `BuildCharacter()` that `ChangeRace` replaces before the generator starts it does not count. DNA and colours are still taken when the race changes. The order of the wardrobe calls, `BuildCharacter()` and `ChangeRace` no longer matters.
- Fixed DNA changes made at play time not redrawing what their color effects control. The UMA 3 character creator (`NewUMAGUI`), `SliderController`, the Timeline DNA track, the Dynamic Expression Player and the SkyCar sample marked the character dirty without running the DNA effects that write colors, so moving **Fitness** changed the bones but not the muscle overlays it fades in. They now apply the build types the DNA reports, as the inspector does. New on `DynamicCharacterAvatar`: `TryGetDNABuildType`, `ApplyDNAChange` and `ReapplyRecipeDNAEffects`; `SetDNA(name, value, true)` now applies the DNA's build types. `SetRawColor` runs the DNA color effects again, so picking a skin color no longer undoes what **Fitness** set.
